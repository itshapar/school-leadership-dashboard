# Архітектурна еволюція безпеки та висновки для масштабування

Цей документ описує перехід проекту `school-leadership-dashboard` від початкової (незахищеної) архітектури до поточної моделі безпеки **Zero Trust**, а також фіксує помилки, що виникли під час цього процесу, та способи їх запобігання в майбутньому.

---

## 1. Початкова Архітектура Безпеки (Pre-Audit)
До проведення аудиту безпеки система працювала за принципом "відкритої двері" для авторизованих користувачів:

*   **Row Level Security (RLS)**: База даних мала формально увімкнений RLS, але політики (наприклад, `admin_all_classes`) дозволяли будь-якому користувачу з роллю `authenticated` (будь-який зареєстрований вчитель) виконувати `ALL` операції над усіма записами.
    *   *Наслідок*: Відсутність приватності даних. Учитель А міг редагувати зірки класу Учителя Б.
*   **API Маршрути (`/api/admin/*`)**:
    *   Використовували `createSupabaseAdminClient` (Service Role Key). Цей ключ повністю ігнорує всі політики RLS.
    *   *Наслідок*: Навіть якби RLS був налаштований правильно, серверний код його обходив.
*   **Middleware**: Захищало лише візуальні сторінки адмін-панелі для перенаправлення на логин, але не блокувало прямі запити до API.
*   **Валідація**: Відсутність серверної перевірки вхідних даних (Payload validation). Система "довіряла" клієнту.

---

## 2. Впроваджені Зміни (Security Hardening)
Для підготовки проекту до масштабування було впроваджено такі зміни:

*   **Ізоляція Даних (Ownership)**: Політики RLS переписані так, щоб доступ надавався лише тоді, коли `teacher_id = auth.uid()`. Тепер дані кожного вчителя ізольовані.
*   **Відмова від Admin-клієнтів**: API маршрути переведені на використання клієнта, що працює в контексті сесії користувача (`supabaseForRls`). Тепер серверний код підпорядковується правилам бази даних.
*   **Middleware Protection**: Додано серверний захист API. Неавторизовані запити до `/api/admin/*` тепер одразу отримують статус `401 Unauthorized`.
*   **Схеми Валідації (Zod)**: Впроваджено схеми для кожного вхідного запиту. Тепер сервер перевіряє типи даних (наприклад, чи є ID справжнім рядком, чи сума зірок є числом) до того, як звертатися до бази.

---

## 3. Виниклі Помилки та Їх Причини
Процес "закручування гайок" виявив кілька критичних проблем:

1.  **RLS Lockout (Блокування власника)**:
    *   *Причина*: В існуючих даних поле `teacher_id` було порожнім (`NULL`). Нові суворі правила просто заблокували доступ до цих "нічийних" класів.
2.  **Пастка `WITH CHECK`**:
    *   *Причина*: У перших версіях виправлення була використана лише умова `USING`. В PostgreSQL для операцій запису (`INSERT/UPDATE`) обов'язково потрібна умова `WITH CHECK`. Без неї база "мовчки" відхиляла зміни.
3.  **Конфлікт валідації (Zod UUID)**:
    *   *Причина*: Спроба змусити всі ID відповідати суворому стандарту UUID (`z.string().uuid()`) призвела до помилок `Invalid request data`, оскільки деякі старі дані або методи їх передачі з фронтенду не проходили цей фільтр.

---

## 4. Дії для Запобігання Проблемам при Масштабуванні

Щоб масштабувати цей проект на нові школи/команди без зупинок у роботі, необхідно:

### А. Попередня Підготовка Даних (Data Migration)
Ніколи не впроваджуйте суворі правила RLS на "живу" базу без перевірки наявності власників у всіх записів.
- **Дія**: Запускати скрипт-аудит: `SELECT count(*) FROM classes WHERE teacher_id IS NULL`. Якщо результат > 0, призначити власника до активації нових правил.

### Б. Прозоре Логування Помилок
Додаток не має видавати загальну фразу "Помилка збереження".
- **Дія**: API має повертати детальний опис (на стадії розробки) та логувати конкретний код помилки PostgreSQL (наприклад, `42501` для RLS violation). Це дозволяє миттєво зрозуміти причину блокування.

### В. М'яка Валідація на Перехідний Період
- **Дія**: Замість `z.string().uuid()`, на етапі переходу використовувати гнучкіший `z.string()`, а сувору перевірку вмикати лише після повної синхронізації типів даних між фронтендом та бекендом.

### Г. "Авто-прив'язка" (Auto-Claim Logic)
Для зручності нових користувачів реалізовано логіку, яка дозволяє вчителю автоматично стати власником "нічийного" класу при першій дії.
- **Дія**: Завжди надавати безпечний спосіб для легітимних користувачів "заявити права" на свої дані, якщо вони ще не прописані в базі.

### Д. Автоматизоване Тестування Безпеки
- **Дія**: Впровадити інтеграційні тести, які перевіряють доступ під різними ролями (User A не може бачити User B). Це єдиний спосіб гарантувати, що зміна одного рядка в SQL не зламає приватність всього проекту.
