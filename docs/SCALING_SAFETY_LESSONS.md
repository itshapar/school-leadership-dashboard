# Архітектурні висновки: Безпека (RLS) та Валідація Дата (Zod)

Цей документ створено для опису інциденту з налаштуванням політик безпеки (Row Level Security), який тимчасово заблокував автозбереження в журналі вчителя. Він слугує посібником для майбутнього масштабування проекту `school-leadership-dashboard`.

## Опис Інциденту
Під час проведення аудиту безпеки та впровадження моделі **Zero Trust**, система була переведена з використання привілейованого серверного клієнта ("admin bypass") на клієнт із жорстким дотриманням **PostgreSQL Row Level Security (RLS)**.
Внаслідок цього виникла проблема "ланцюгової реакції", яка заблокувала можливість оновлення журналу:
1. Існуючі "legacy" класи не мали визначеного `teacher_id` (значення було `NULL`).
2. Оновлення RLS з правилом "дозволити вчителю редагувати тільки свої класи" автоматично заблокувало всі класи, де `teacher_id IS NULL`.

Процес ремонту зайняв час через три "приховані" пастки:
1. **Пастка PostgreSQL RLS (`WITH CHECK`)**: Щоб дозволити вчителям "забирати" собі класи, було створено правило `FOR ALL USING (...)`. Однак у PostgreSQL для операцій `INSERT` та `UPDATE` обов'язково потрібне правило `WITH CHECK`. Без нього база даних мовчки (без генерації зрозумілої помилки) відхиляє спроби запису.
2. **Надмірно жорстка валідація (Zod)**: Впроваджена схема `z.string().uuid()` заблокувала запити на рівні серверу, оскільки деякі існуючі або тимчасові ідентифікатори (ID) з фронтенду не відповідали суворому формату UUID. Запит відхилявся ще до бази даних.
3. **Відсутність прозорого логування**: Сервер просто віддавав клієнту базове повідомлення *"Invalid request data"* або *"Помилка бази даних"*, що не дозволяло одразу побачити реальну причину відмови на клієнті.

## 🛠 Уроки та Правила для Майбутнього Масштабування

Щоб уникнути повторення ситуації при розширенні проекту на десятки чи сотні вчителів, ми маємо дотримуватись наступних інженерних практик:

### 1. Data Migration (Міграція Даних) Перш за Все
Ніколи не застосовувати жорсткі правила до баз даних без попередньої підготовки наявних даних.
- **Дія**: Перед розгортанням нових RLS правил, обов'язково треба запускати скрипти міграції (Data Backfill), щоб перевірити, чи немає порожніх критичних полів (наприклад, `teacher_id`), і заповнити їх (присвоїти існуючі класи конкретному тестувальнику/адміну).

### 2. "Тіньовий Режим" для Валідації (Shadow Mode / Graceful Degradation)
Введення жорсткої валідації (наприклад, Zod UUID або суворих типів) на "живу" систему має відбуватися м'яко.
- **Дія**: Замість того, щоб одразу повертати помилку `400 Bad Request`, спершу логувати невідповідності (Warning), але пропускати їх. І лише коли ми впевнимось, що фронтенд генерує 100% правильні типи даних, переводити валідацію в режим "Блокування".

### 3. Комплексне Логування та Моніторинг (Sentry / Vercel Logs)
Додаток не повинен "мовчати" про причину проблеми.
- **Дія**: У всіх `try / catch` блоках (особливо в API) ми маємо фіксувати реальну причину: `console.error("Supabase Error:", error.message, error.hints)`.
- **Дія**: На продакшені необхідно інтегрувати сервіси моніторингу помилок (наприклад, **Sentry**), щоб ми миттєво отримували сповіщення: *"Учитель X не зміг зберегти зірку. База відхилила запит через правило 'admin_all_star_entries'"*.

### 4. Автоматизоване Тестування (End-to-End Tests)
Зміни в RLS та безпеці неможливо надійно перевірити "на око" в базі.
- **Дія**: При масштабуванні нам необхідно налаштувати **Playwright / Cypress** тести. Після кожної зміни тест повинен автоматично спробувати: залогінитись як Учитель А -> спробувати поставити зірку своєму учню (має працювати) -> спробувати поставити зірку учню Учителя Б (має заблокувати).

### 5. Повна Структура RLS (Обов'язковий `WITH CHECK`)
- **Правило**: При написанні політик `CREATE POLICY ... FOR ALL`, завжди використовуйте комбінацію `USING(...)` та `WITH CHECK(...)`. Це гарантує, що операції оновлення та створення даних не будуть тихо "проковтнуті" базою.
