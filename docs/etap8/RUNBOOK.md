# Етап 8 — Runbook: безпечне завершення переходу

## Що з'ясувалось на старті

Етап 8 у роадмапі описаний як «міграція поточних даних у нову мультитенантну
структуру». **Цю міграцію вже виконано** — міграціями `013a`, `014`, `015`,
`016`, `019` під час Етапів 1 і 3. Перевірено на проді 2026-08-20:

| Перевірка | Факт |
|---|---|
| Класів / власників | 6 / 1 (усі під акаунтом Andrew, `teacher_id NOT NULL`) |
| Класів без власника | 0 |
| Усі 6 у паралелі «7» | так (створена міграцією 014) |
| Нові 10-символьні коди | так, усі 6 |
| `star_entries` без `entry_type_id` | 0 із 1374 |
| Типи нарахувань | 18 = 3 × 6 класів |
| Класові призи | 12 = 2 × 6, пороги збігаються з легасі 1-в-1 |
| Індивідуальні призи | 24 = 4 × 6 |
| Учні / уроки | 87 / 140 |

Писати міграцію даних зараз означало б no-op або дублювання. Тому Етап 8
перенацілено на те, чого справді бракує: **безпечне застосування `020`** —
єдиної незворотної міграції проєкту (`DROP COLUMN`, `DROP TYPE`) — плюс
`024`+`026` і відключення старих кодів.

Усі чотири вимоги збережено: dry-run, звірка до/після, бекап і відкат,
рішення щодо старих кодів.

## Порядок виконання

Кроки строго послідовні. Кожен має умову «не йти далі, якщо…».

### 0. Задеплоїти фронтенд Етапу 6 + 6.1

Мердж `etap6` → `main` → production-деплой.

**Не йти далі, поки не перевірено вручну під своїм логіном:**

- журнал класу: виставити оцінку, перезавантажити сторінку — значення на місці
  (перевірка нового `upsert` на `entry_type_id`);
- налаштування класу: створити тип нарахування і класовий приз;
- майстер `/admin/onboarding` наскрізно;
- публічна сторінка класу показує призи й прогрес.

> Чому це блокує все інше: `020` дропає легасі-стовпці, на які старий
> фронтенд ще дивиться. Порядок «спершу код, потім дроп» — той самий, що
> в 013a→013b і 015→020.

### 2. Бекап

Див. [`scripts/etap8/02_backup.md`](../../scripts/etap8/02_backup.md).

**Не йти далі, поки бекап не завершений.** Запиши сюди факт:

```
Тип бекапу:  ____________________  (PITR / on-demand / pg_dump)
UTC-час:     ____________________
Ким:         ____________________
```

### 3. Знімок «до»

```bash
npx tsx scripts/etap8/snapshot.ts before
```

Створює `docs/etap8/snapshot-before.json`: глобальні лічильники, по кожному
класу — записи/суми/конфігурація призів і типів, по кожному учню — сумарні
зірки. Персональних даних у файлі немає (лише UUID-и, назви класів і числа),
тому його можна комітити як доказ звірки.

Прогін 2026-08-20: `класів 6 · учнів 87 · уроків 140 · нарахувань 1374 · сума 1495`.

Сам інструмент перевірено: на незмінених даних дає нуль розбіжностей, а на
штучно зіпсованому знімку ловить усі три підміни (клас, конфігурація призів,
окремий учень) і завершується кодом 1.

### 4. Застосувати 020

```
supabase/migrations/020_post_deploy_cleanup.sql
```

Що робить: знімає три тригери-містки, перевизначає обидві публічні RPC без
легасі-ключів, дропає `star_entries.type`, `classes.game_day_threshold`,
`classes.pizza_day_threshold`, `class_prizes_given.prize_type`,
`class_prizes.legacy_source`, `entry_types.legacy_type` і два enum-типи.

### 5. Звірка «після»

```bash
npx tsx scripts/etap8/snapshot.ts after
```

Очікується `✅ Розбіжностей немає`. **Будь-яка розбіжність — перехід до
розділу «Відкат».**

Далі — димова перевірка живого застосунку:

```bash
npx tsx scripts/test-fullname-leak.ts KBCDTRVGM4
```

Має додатково повідомити `легасі-ключа type немає — міграція 020 застосована`.

І вручну: виставити оцінку в журналі та перезавантажити сторінку. Це
найважливіший тест — саме тут `020` могла б зламати `upsert`, якби не
`025`/`025a`.

### 6. Роздати PIN-и

`/admin/[клас]/students` → «PIN-И КЛАСУ» → скопіювати/роздрукувати пам'ятку.

PIN-и показуються **один раз**. Робити по одному класу за раз.

**Не йти далі, поки PIN-и не в руках учнів** — крок 7 закриває їм старий
шлях доступу.

### 7. Закрити персональний дашборд: 024 + 026

```
supabase/migrations/024_student_dashboard_lockdown.sql
supabase/migrations/026_lockdown_fix_authenticated.sql   ← обов'язково разом
```

> **Чому 026 обов'язкова.** `024` відкликає доступ лише в `PUBLIC, anon`,
> супроводжуючи це коментарем «authenticated не мав і не має». Коментар
> помилковий: `019` видала `GRANT … TO anon, authenticated`, перевірено на
> проді. Без `026` дірка лишиться відкритою для будь-кого з акаунтом —
> а реєстрація відкрита. Маючи код класу (який ми самі радимо давати
> батькам), така людина отримала б персональні дашборди учнів **разом із
> нотатками вчителя**. Це рівно той ризик, заради якого писалась `024`.

Перевірка після застосування — має лишитись **тільки** `service_role`:

```sql
select coalesce((select string_agg(g, ', ' order by g)
       from unnest(array['anon','authenticated','service_role','public']) g
       where has_function_privilege(g, p.oid, 'EXECUTE')), '—')
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname='public' and p.proname='public_student_dashboard';
```

Контрольний позитивний тест: учнівський вхід за PIN мусить **далі працювати**
(`student_dashboard_by_session` викликає RPC зсередини як `SECURITY DEFINER`,
тому гранти викликача її не стосуються).

### 8. Відключити старі 4-значні коди

```
scripts/etap8/04_legacy_codes.sql
```

Рішення власника: прибрати. Поки старий код живий, простір перебору — 10 000,
і 10-символьні коди Етапу 1 не дають нічого.

Дитина зі старою пам'яткою побачить не 404, а екран «Цей код більше не діє —
візьми новий у вчителя» ([`LegacyCodeNotice`](../../components/LegacyCodeNotice.tsx)).
Екран показується для **будь-якого** 4-значного коду — перевіряється лише
формат, тож він не працює оракулом «такий клас є».

## Відкат

### Сценарій A — проблему помітили одразу, нових даних немає

Відновлення з бекапу (крок 2). Точне, без обмежень.

### Сценарій B — з 020 попрацювали, нові бали вже нараховані

Відновлення з бекапу коштувало б утрати робочого дня. Тому:

1. `scripts/etap8/03_rollback_020.sql` — реконструює enum-типи, легасі-стовпці
   й тригери-містки з нових таблиць, зберігши всі нові дані.
2. Повторно застосувати `019_limits_and_public_rpc.sql` — він ідемпотентний
   і поверне RPC зі старими ключами.
3. Відкотити деплой у Vercel на попередній production-деплой.
4. `npx tsx scripts/etap8/snapshot.ts after` — звірити з `snapshot-before.json`.

**Межа точності реконструкції:** нарахування, зроблені після `020` типом, який
учитель створив сам («Домашнє завдання»), не мають відповідника серед трьох
значень старого enum. Їм проставляється ярлик за правилом тригера-містка з
`015` (`sign < 0` → penalty, `is_lesson_bound` → lesson, інакше bonus). Суми
балів і прив'язка до учнів **не страждають** — приблизним стає лише легасі-
ярлик `type`, який після `020` нікому не потрібен.

## Що лишається після Етапу 8

- `star_entries.student_id` лишається nullable — класове нарахування досі
  один рядок, а не fan-out. Рішення свідомо відкладене ще в коментарі до `020`.
- Сторінка «швидкий урок» `/admin/[клас]/lesson` працює, але нікуди не
  залінкована — або повернути в тулбар, або прибрати. Окреме рішення.
- Leaked password protection у Supabase Auth вимкнено, хоча текст на
  `/register` обіцяє перевірку пароля на витоки. Вмикається перемикачем у
  Dashboard → Authentication → Policies.
